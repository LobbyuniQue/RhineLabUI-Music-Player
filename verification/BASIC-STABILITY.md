## 第二批 · 千首歌单的三维浏览

**06 · 后段渲染。** 旧逻辑为所有可能的行距预留卡片，越往后走，传给逐张筛选的候选就越多。现在把相机可见区域换算成当前行距下的行号范围，保留卡片尺寸、升起高度和额外阴影覆盖。渲染比例、模型和画质设置沿用原值。

以 `4f01cd1` 为对照，在同一 1920 × 1080 概览相机下测量。分组首曲和第 1000 首分别位于逻辑行 12 和 1011。表内统计进入逐张筛选的卡片数，最后一列为两版共同的可见卡片数。

| 音乐行距 | 首曲候选（旧 → 新） | 第 1000 首候选（旧 → 新） | 第 1000 首可见 |
| --- | ---: | ---: | ---: |
| 0.62 | 508 → 453 | 14,941 → 453 | 317 |
| 4.05 | 604 → 72 | 96,232 → 72 | 48 |
| 8.00 | 880 → 36 | 189,843 → 36 | 25 |

三种行距、四个浏览位置各做 25 次轨道微移，300 次对照逐一核对了可见卡片的列、行与顺序。常规回归还覆盖五种宽高比、概览与详情相机、行距渐变、阴影扩展和正反向滚动。

在独立静音 Edge 中用 1000 首合成歌曲打开实际页面，视口为 960 × 600，默认行距为 4.05。旧版从第 1 首到第 989 首，候选由 626 增至 101,120，新版两处均为 75。四次测量都绘制 51 张阵列卡片，渲染统计均为 375,226 个三角形。浏览器采用 SwiftShader 软件渲染，无法据此估算用户显卡上的帧率。

把行距调至最短的 0.62 后，旧版同两处的候选分别为 536 和 15,705，新版均为 471。密集排列时相机里本来就能看到更多卡片，因此仍需绘制更多实例。

**07 · 循环浏览后错歌。** 场景把远离中心的局部坐标移回中心时，原先有些交互会直接把新坐标当成曲库位置。现在先加回累计的行、列偏移，再按目标分组的实际曲数查找。封面分配、悬停、点击和拖动都从同一逻辑位置取得曲目。键盘导航和检索跳转使用对应的反向换算。关闭三维画面时连同选中卡片保存坐标原点，重新开启时一并恢复。

回卷专项使用三个长度分别为 7、10、13 首的分组，正反向跨越 2048 的坐标边界后，检查邻卡的悬停、拖动选曲和三维恢复。另用 21、65、300 首的分组检查跨列和任意歌曲跳转。常规检查现包含上述回归。

在 Edge 中沿同一路径浏览至逻辑行 2412，局部行回到 12，累计偏移为 2400。此时第 401 首位于相机焦点。旧版在该卡上悬停和点击都识别为第 1 首，新版两次均识别为第 401 首。

另在新版选取固定屏幕坐标，实际点击当前卡片的上一张。选中第 1 首时，悬停显示第 1000 首，点击得到 `M-1000 / track-999`。回卷后选中第 401 首时，同一位置悬停显示第 400 首，点击得到 `M-400 / track-399`，核对了界面编号和曲库中的真实 ID。

本批 `npm run check` 和 `npm run build` 通过，归位及回卷专项共 25/25 通过。基础检查中，VLC 状态测试原先缺少桥接所读取的音频输出参数，已在模拟环境补入 `dummy` 并断言状态回执。离线构建指纹为 `d11e4ed52f6138cb`。页面测试只注入合成曲目元数据，独立浏览器使用 `--mute-audio`。本批未重跑完整浏览器播放与 VLC 集成套件。原始对照数据分别位于本机 `.local/scene-stability-20261122/` 和 `.local/render-study-20261122/`。
